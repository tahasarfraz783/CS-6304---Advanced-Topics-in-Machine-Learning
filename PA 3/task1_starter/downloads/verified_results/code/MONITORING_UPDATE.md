# Live progress and recovery update

The original evaluation code generated GSM8K answers serially with no visible question
counter and saved them only after the full benchmark. That made the paid run hard to
monitor and meant an interruption could lose all unfinished-benchmark generations.

This update fixes visibility and recovery. It does NOT promise faster generation or change
the required dataset, one-epoch budget, methods, caps, greedy decoding, or scoring rules.

## What now appears

```text
[PHASE] baseline_0000 | GSM8K answer generation (not prompt preparation) 0/1319 answers
[HEARTBEAT] baseline_0000 | ... question ID 0 | current answer: 356 decode steps
[PROGRESS] baseline_0000 | ... 1/1319 answers | elapsed 8s
```

Those numbers are illustrative. Completed answer counts are emitted AFTER the answer is
saved. Decode steps are observed forward calls, not a claim that the answer is correct.
A heartbeat appears every 15 seconds. Its activity age distinguishes an alive process
from new measured work; a heartbeat by itself does not prove generation is advancing.
After three new answers, the current generation phase gets a measured remaining-time
estimate. That estimate is NOT an ETA for the entire five-method experiment.

Other phases identify model loading/export, data filtering, SVD bases, activation caching,
candidate-likelihood scoring, each optimizer update, qualitative responses, and archives.

## Training recovery checkpoints

The four required checkpoints at updates 312, 625, 937, and 1250 are retained. A rolling
recovery checkpoint is additionally written every 100 updates. Only the newest extra
rolling checkpoint is kept; it is removed once a newer required/rolling checkpoint has
been written successfully. Required checkpoints are never removed by this pruning.
This adds storage/write overhead, but limits lost work without keeping dozens of full
optimizer states. At most one extra full rolling checkpoint plus its temporary replacement
is needed during an active method. Each save prints CHECKPOINT SAVED with its path/size.

Recovery includes trainable weights, Adam moments, scheduler, gradient scaler, RNG, and
completed update (which determines the exact next example in the fixed dataset order).
The launcher chooses the newest required OR rolling checkpoint when resuming. Additional
recovery writes do not change the examples, epoch budget, or evaluation schedule.

## Where to look

Under `outputs/assignment/`:

| File | Meaning |
|---|---|
| `progress.txt` | Latest readable worker line |
| `progress.json` | Latest structured phase/count/activity snapshot |
| `progress_events.jsonl` | Timestamped history of phases/progress/heartbeats/errors |
| `pipeline_status.json` | Current worker/stage or final success/failure |
| `evaluations/*/gsm8k_generation_progress.jsonl` | Each completed answer and generation metadata |
| `evaluations/*/scores_partial.json` | Scores as each benchmark finishes |

Commands:

```bash
python run.py --mode status     # returns immediately, no GPU/model load
python monitor.py              # live viewer; Ctrl+C closes the VIEWER only
```

The viewer exits when the pipeline records completion/failure. Snapshot age is displayed;
if a process was killed or the machine stopped, an old "running" snapshot is not presented
as proof of current activity. The viewer does not start training, stop a cloud instance,
or change billing.

## Apply on the stopped cloud instance

1. Keep the existing instance/storage; do not destroy it or delete outputs.
2. Resume it only when ready to upload `task1_monitoring_update.zip`.
3. Upload the ZIP at the same Jupyter root where the original ZIP appeared.
4. In a terminal, confirm the original run is not still running, then:

```bash
python -m zipfile -e /task1_monitoring_update.zip /home
cd /home/task1_starter
python run.py --mode verify-eval
```

The short preflight loads the existing starting model, generates two responses capped at
eight tokens, verifies cache reuse, and scores one continuation. It is not another full
smoke test. It creates only separate `evaluation_preflight/` outputs. Requirements are
unchanged, so no package reinstall is needed if the earlier installation succeeded.

Once preflight passes:

```bash
nohup python -u run.py --mode run > experiment_v2.log 2>&1 &
python monitor.py
```

The launcher reuses prepared examples/bases and completed checkpoints/evaluations. It
also runs the short preflight before the full experiment. Completed generation requests
are matched by document ID, prompt, and generation arguments within their model-condition
directory; changed requests cannot silently reuse an old answer. Completed benchmark
scores and qualitative responses are reused too.

Answers generated by the ORIGINAL silent process were not saved individually. If that
process was stopped before producing its benchmark output, those in-memory answers cannot
be recovered. Replacing source files cannot change an already-loaded Python process.

## Billing and results

The experiment still does NOT automatically stop the cloud instance. After completion,
download/verify the results and model ZIPs, then stop/destroy the instance as appropriate.
Original training/recovery states and model exports are preserved. New progress files and
answer caches are also included in the results archive, allowing offline inspection.

## Verification

Tests cover the original training methods plus progress state, heartbeat distinction,
failure reporting, interrupted-cache recovery, request-change invalidation, actual pinned
HFLM generation with a tiny local Qwen model/tokenizer, inference-hook removal, no model
calls on cached repeat, and candidate-likelihood scoring. No assignment benchmark numbers
or full-run speed claims are derived from these tiny tests.
